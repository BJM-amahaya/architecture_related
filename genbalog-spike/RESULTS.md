## 4. 判定

- (a) 初回コンパイル実測最大値 < 25秒: **[x] Yes**（2026-08-07・2枚条件で 3,479ms。5枚条件でも当日初回 7,779ms で数分規模のコンパイルは観測されず）
- (b) ウォームアップで初回を利用者経路から確実に除外できる: **[x] Yes**（工程2でデプロイ後・スキーマ変更後の事前呼び出しを必須化する前提。ただし (a) を単独で満たすため本判定は (a) に依拠する）
- 定常 P95 < 25秒（十分な余裕あり）: **[x] Yes** — **6,691ms**。目安 25,000ms に対し **18,309ms の余裕**（バジェット消費率 **26.8%**）
- 判定: **[x] 同期継続 → `03_step2_ai.md`** / [ ] 非同期化 → `03b_step2_async.md`

### 結論と根拠

5枚・N=20 の定常計測で **P95 = 6,691ms**、最大でも 7,779ms。同期継続の目安 25,000ms（AppSync 30秒 − 安全マージン5秒）に対して **約3.7倍の余裕**があり、失敗は 20回中 0件。`outputConfig` 方式で懸念されていた「初回スキーマコンパイル最大数分」は、**Tool Use 方式では一度も観測されなかった**。よって **同期方式（AppSync custom query 直呼び）を採用**する。

### 🔴 この判定に付く重要な留保（工程2で必ず解消すること）

**本計測は「ローカルPC → Bedrock の単発呼び出し」のみを測っており、以下を含んでいない。**

| 未計測の要素 | 影響 |
|---|---|
| Lambda コールドスタート | 初回起動で数百ms〜数秒の追加 |
| S3 からの画像取得（5枚） | ネットワーク往復 × 5 の追加 |
| AppSync のリクエスト経路 | オーバーヘッド追加 |
| 弱回線（現場のモバイル回線） | アップロード時間の大幅増。**proposal §6 が中心ユースケースと明記** |

したがって **25秒バジェットとの比較は楽観側に振れている**。18.3秒の余裕は上記を吸収できる見込みだが、**工程2で Lambda 経由の E2E 再計測を行い、この判定を確定させること**。E2E で P95 が 25秒に迫る場合は `03b_step2_async.md`（非同期）へ切り替える。
