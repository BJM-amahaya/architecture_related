# 工程4 実装手順書：品質評価（AI出力の合否判定）

対象アプリ: 現場AI日報「GenbaLog」（建築業界向け PoC / デモアプリ）

## 目的・前提

**目的:** 固定評価セットを使って `generateReport` の AI 出力（日報4項目：作業内容／進捗／安全・懸念／翌日の予定）の品質を定量測定し、proposal §1「撮って書き足すだけで日報が仕上がる」の受入可否を KPI で判定する。不合格時はプロンプト／JSON Schema を調整し、`promptVersion` を更新して再評価を回す。

**依存する工程: 工程3まで完了**
- 工程0：東京 In-Region の `anthropic.claude-haiku-4-5-20251001-v1:0`（`ap-northeast-1`）疎通・同期/非同期方式が確定済み
- 工程1：`Site`／`Report`／`Photo` の認可付き Data／Storage が動作
- 工程2：`generateReport`（custom query）が Structured Outputs で日報4項目を返却。冪等キー `reportId + imageSetHash + inputHash + promptVersion + modelId + schemaVersion` が実装済み
- 工程3：撮影＋最小テキスト入力 → 生成 → 確認・微修正 → 確定 → 一覧・PDF 出力の UI が一気通貫で動作

**この手順書で使うモデル・データモデル（厳守）:**
- Bedrock モデルID: `anthropic.claude-haiku-4-5-20251001-v1:0`、リージョン: `ap-northeast-1`
- データモデル: `Site`（現場）／`Report`（日報）／`Photo`（写真）
- 冪等キー: `reportId + imageSetHash + inputHash + promptVersion + modelId + schemaVersion`（`inputHash` はテキスト入力＝reportDate/workType/memo/nextPlanInput のサーバー側正規化ハッシュ。`SCHEMA_VERSION` は JSON Schema 構造変更時にインクリメントする定数＝03_step2_ai.md で定義）

**process.md ゲートとの対応（重要）:**（process.md v2／2026-07-11 に準拠）
本工程4の**フル KPI 測定**（ステップ1〜4：充足率≥90%・事実誤認率≤5%・要確認項目が推測で埋まらない）は、process.md v2 §2/§3 の **S-accept（提案受入可）の必須条件**であり、**S-tech（技術共有可）の必須条件ではない**。ただし**ステップ0 の最小品質スモークは S-tech に必須**である（process.md v2 §2 S-tech）。したがって「本工程はゲート必須ではない」という旧表現は正確ではなく、正しくは**「S-tech のゲート必須ではないが最小品質スモークは必須、フル KPI は S-accept の必須条件」**と位置づける。フル KPI は S-tech 昇格の前提にはしないが、S-accept の到達には満たすことが必須。

## ステップ0. 最小品質スモーク（S-tech 前に必須）

**位置づけ:** process.md v2（2026-07-11）§2 の **S-tech 必須条件**。フル評価（ステップ1〜4）とは**独立**に、共有（EAS 内部配布／通しデモ）の**前に必ず**実施する。少数ケースで「明白な捏造・断定を出さない」ことだけを短時間で確認する軽量チェックであり、フル KPI（S-accept）の代替ではない。

**前提:** 実施前に工程2のウォームアップ（初回コンパイル・24時間キャッシュ）を実行してから測る（フル評価と同じ注意。proposal §6・§7）。

**内容:** 少数ケース（各1〜2件、**合計3〜6件**）で以下のみを確認する。

- (a) **無関係写真**で作業内容・数量・翌日工程を**捏造しない**（`要確認`／`不明`／空欄になる）。
- (b) **不鮮明写真**で**断定しない**（判読困難な内容を言い切らない）。
- (c) **テキスト欠落入力**（当日メモ空欄・翌日予定空欄）で、該当項目を**推測で埋めない**（`要確認`／空欄になる）。
- (d) **安全項目**で「問題なし」「安全確認済み」等の**断定を生成しない**（`safety.confirmed`／`safety.unconfirmed` の分離が機能している）。

**判定:** 1件でも捏造・「問題なし」生成があれば **S-tech をブロック**し、ステップ4の調整（プロンプト／スキーマ）へ回す。修正後にスモークを再実施して全件クリアを確認する。

**記録:** 次の簡易表を作業記録に残し、**S-tech の証拠**として提出する（process.md v2 §2）。

```markdown
| caseId | 写真カテゴリ | 入力欠落 | 捏造なし(○/×) | 「問題なし」なし(○/×) | 証拠(出力抜粋・スクショ等) |
|---|---|---|---|---|---|
| S01 | 無関係写真 | なし |   |   |   |
| S02 | 不鮮明写真 | なし |   |   |   |
| S03 | 代表写真 | 当日メモ空欄 |   |   |   |
| S04 | 代表写真 | 翌日予定空欄 |   |   |   |
```

> 本スモークは共有前の最低限の事実性チェック。フル KPI（充足率・事実誤認率・要確認率）はステップ1〜4で S-accept 向けに別途測定する。

## ステップ1. 固定評価セットを作る

AI 出力の「事実性」を再現性をもって測るため、**入力を固定した評価セット**を用意する。乱数的に写真を差し替えると KPI が比較不能になるため、セットは一度作ったら固定し、`promptVersion` を上げても**同じ入力**で回す。

### 1-1. 写真4カテゴリ × 件数目安

proposal §9 工程4 の指定4カテゴリを用意する。**合計12〜16件**（各カテゴリ3〜4件）を目安とする（少なすぎると率が粗く、多すぎると手評価コストが増えるため）。

| カテゴリ | 内容 | 件数目安 | 評価の狙い |
|---|---|---|---|
| 代表写真 | 配筋・型枠・打設など工種が明確に写った鮮明な現場写真 | 3〜4件 | 必須項目充足率・日本語品質の基準確認 |
| 不鮮明写真 | 手ブレ・逆光・暗所・被写体が小さい等で判読困難 | 3〜4件 | 推測で断定せず `要確認`／`不明` を返すか |
| 無関係写真 | 現場と無関係（休憩所・空・書類・人物のみ等） | 3〜4件 | 写真から作業内容を捏造しないか（事実誤認の検出） |
| 情報不足写真 | 工種は写るが数量・進捗・安全状況が写真だけでは確定不能 | 3〜4件 | 数量等を推測で埋めず `要確認` にできるか |

- 写真は工程3と同条件（長辺1,568px に圧縮、1日報あたり枚数上限＝例3枚）で用意する（proposal §6 と整合）。
- 個人情報・実在人物が特定できる写真は避け、PoC 用に撮り下ろす。

### 1-2. 付随テキスト入力のパターン設計

proposal §3 の入力5項目（**現場／日付／工種／当日メモ／翌日予定**）を、写真カテゴリと**独立に**振ることで「テキストを主根拠、写真を補助」という事実性設計（proposal §3）を検証する。各写真に対し、少なくとも次の3パターンを組み合わせる。

| パターン | 現場 | 日付 | 工種 | 当日メモ | 翌日予定 | 検証の狙い |
|---|---|---|---|---|---|---|
| P1: 十分入力 | 有 | 有 | 有 | 具体的に記載 | 具体的に記載 | 充足率が上がるか（テキストを主根拠にできるか） |
| P2: メモ空欄 | 有 | 有 | 有 | 空欄 | 有 | 当日メモが無いとき作業内容を写真だけで断定しないか |
| P3: 翌日予定空欄 | 有 | 有 | 有 | 有 | 空欄 | 翌日の予定を推測で捏造せず `要確認`／空欄にするか |

- 特に**無関係写真 × P1（十分入力）** の組で「テキストが正しければ写真の無関係さに引きずられないか」、**代表写真 × P2/P3** で「写真が良くてもテキスト欠落項目を推測で埋めないか」を必ず含める。
- 数量（施工数量・作業員数）は proposal §3 のとおり写真から確定不能なので、テキストにも入れない項目を用意し `要確認` 化を確認する。

### 1-3. 評価セットの保管方法

再現性と証拠保全（proposal §9「ログに記録する項目」と整合）のため、リポジトリ内に評価セットを固定保存する。

- 保存先: `spec/plan7/eval/`（新規）
  - `spec/plan7/eval/photos/`：評価用写真（`c1_daihyo_01.jpg` のようにカテゴリ接頭辞で命名）
  - `spec/plan7/eval/cases.md`（または `cases.csv`）：ケース定義表。列は `caseId / 写真ファイル / カテゴリ / 入力パターン / 現場 / 日付 / 工種 / 当日メモ / 翌日予定 / 期待挙動メモ`
  - `spec/plan7/eval/results/`：測定結果（ステップ3のテンプレートを `results/<promptVersion>_<測定日>.md` で保存）
- `caseId` は固定（例 `C01`〜`C16`）。`promptVersion` を上げても `caseId` と入力は変えず、`promptVersion` ごとに results ファイルを追加する。
- 写真本体・プロンプト本文は CloudWatch 等の通常ログには出さない（proposal §6・§9）。評価セットはリポジトリ内でのみ管理する。

## ステップ2. KPI を定義し測定する

各 KPI は「計算式」と「判定方法」を明示する。測定は評価者（人）が AI 出力と入力・写真を突き合わせて手判定する。1ケース＝日報1件（4項目）を評価単位とする。

### 2-1. 必須項目充足率（合格ライン ≥90%）

- **定義:** 日報4項目（作業内容／進捗／安全・懸念／翌日の予定）のうち、「適切に埋まっている」項目の割合。`要確認`／`不明`／空欄も、**推測で断定していなければ「適切に充足」とみなす**（事実性を優先するため、無理に埋めた断定はむしろ減点対象＝2-2で数える）。
- **計算式:**
  ```
  必須項目充足率 = 適切に充足した項目数 / (ケース数 × 4項目) × 100
  ```
- **判定方法:** 各ケースの4項目を評価者が○（適切に充足＝根拠のある記述、または正しく `要確認`／`不明`）／×（欠落・空のまま放置・意味不明）で判定し集計。**≥90% で合格。**

### 2-2. 事実誤認率（合格ライン ≤5%）

- **定義:** 「**写真・テキスト入力のいずれからも確認できないことを、断定して書いた**」項目の割合。proposal §3 の禁止事項（推測で埋める・「問題なし」生成）の違反を数える。
- **「断定して書いた」件数の数え方（評価者の判定基準）:** 次のいずれかに該当する項目を1件として数える。
  1. 写真にもテキストにも根拠がない工種・数量・作業員数・翌日工程を**言い切っている**（例: 入力にないのに「配筋100㎡完了」）
  2. 無関係写真・不鮮明写真から作業内容を**創作している**
  3. 安全項目で、画角外・未確認の事項を「問題なし」「安全確認済み」と**断定**している（proposal §3 の「問題なし」禁止・確認/未確認分離の違反）
  - `要確認`／`不明`／「（画角外・未確認）」と明示したものは**事実誤認に数えない**（正しい振る舞い）。
- **計算式:**
  ```
  事実誤認率 = 断定した誤認項目数 / (ケース数 × 4項目) × 100
  ```
- **判定方法:** 全ケース×4項目を走査し該当件数を数える。**≤5% で合格。** 無関係・情報不足カテゴリで誤認が出やすいので重点確認する。
- **サンプル数の限界（必ず併記）:** 12〜16件（×4項目＝48〜64判定）では ≤5% の判定粒度が粗い。例：4項目×12件＝48判定では誤認2件で 4.17%、3件で 6.25% となり、**1件の差で合否が変わる**。results にはサンプル数と信頼性の限界を必ず併記し、**境界値（誤認率が概ね 4〜6%）の場合は件数を増やすか「保留」と記録**して即断しない（process.md v2 §2 S-accept の「サンプル数の限界を results に併記」に対応）。

### 2-3. 要確認率（推測で埋まっていないことの確認）

- **定義:** `要確認`／`不明` を返すべきケース（写真・入力から確定できない項目）で、実際に `要確認`／`不明`（または「（画角外・未確認）」）が返っている割合。**低すぎる＝推測で埋めている**サインとして使う（充足率と対で見る指標）。
- **計算式:**
  ```
  要確認率 = 正しく要確認/不明を返した項目数 / (要確認/不明を返すべき項目数) × 100
  ```
  - 「要確認/不明を返すべき項目数」は、ステップ1-2 の期待挙動メモ（P2 の作業内容、P3 の翌日予定、情報不足写真の数量 等）を分母に取る。
- **判定方法:** 期待どおり `要確認`／`不明` になっていれば○。**確定不能なのに具体値・断定文が入っていたら×**（これは 2-2 の事実誤認にも計上）。要確認率が低いのに充足率が高い場合は「推測で埋めて充足率を水増し」している疑いとして 2-2 を精査する。

### 2-4. 修正文字率・作成時間短縮率（ベースライン比較）

いずれも「手作業日報」とのベースライン比較で測る。ベースラインは**同一ケースを人が手入力で日報化**した文章・所要時間とする。

- **修正文字率**
  - **定義:** AI ドラフトを確定文にするために評価者が修正した文字量の割合。小さいほど「そのまま使える」。
  - **計算式:**
    ```
    修正文字率 = 変更文字数(挿入+削除) / AIドラフトの総文字数 × 100
    ```
    - 変更文字数は確定文と AI ドラフトの差分（例: `diff` のレーベンシュタイン相当、または挿入・削除文字の単純合算）で数える。ケースごとに算出し平均を取る。
- **作成時間短縮率**
  - **定義:** 手作業日報の作成時間に対し、GenbaLog（撮影・入力〜確認・微修正で確定まで）で短縮できた割合。proposal §1 の体験価値の定量指標。
  - **計算式:**
    ```
    作成時間短縮率 = (手作業所要時間 − GenbaLog所要時間) / 手作業所要時間 × 100
    ```
  - **測定手順:** 代表数ケース（例 代表写真3件）で、(a) 同一入力から人が手で日報を書く時間、(b) GenbaLog で生成→確認→微修正→確定する時間をストップウォッチで計測。撮影・アップロード時間の扱い（含む／含まない）を results に明記し、条件を固定して比較する。
  - 注: proposal §9 では合格ラインは充足率・事実誤認率・要確認で定義。修正文字率・作成時間短縮率は**受入の補助指標**として測定・記録し、悪化傾向があればプロンプト調整の判断材料にする。

## ステップ4. 不合格時の調整手順

KPI が合格ラインに達しない場合、原因別に**プロンプト**または **JSON Schema** を調整し、`promptVersion` を上げて再評価する。

### 4-1. プロンプト調整

- 安全項目は「（確認できた事項）」と「（画角外・未確認）」を**分離して出力**させ、「問題なし」「安全確認済み」を**生成禁止**にする（proposal §3）。
- 「写真・入力から確認できない工種・数量・作業員数・翌日工程は、推測で書かず `要確認`／`不明`／空欄にする」ことを明示的に指示。
- 無関係・不鮮明写真では「写真から作業内容を判読できない場合は作業内容を創作しない」ことを追記（事実誤認率対策）。

### 4-2. JSON Schema 調整

- 各項目が `要確認`／`不明`／空欄を返せるよう、値を許容する（例: enum に `要確認` を含める、または `nullable`／空文字許容）。JSON Schema は形式のみ保証し内容の事実性は保証しないため、事実性はプロンプトと評価で担保する（proposal §3）。
- 安全項目は工程2の実装どおり「確認できた事項」と「未確認事項」を分離したネスト構造（Bedrock 出力スキーマ・GraphQL 戻り値とも `safety.confirmed` / `safety.unconfirmed`。03_step2_ai.md 参照）になっており、2-2 の断定検出を機械的に行える。
- Structured Outputs は `bedrock-runtime` の Converse／InvokeModel で利用（Messages API 経路では不可）。**スキーマを変更したら初回コンパイル（最大数分）とキャッシュ24時間に注意**し、工程2 のウォームアップを再実行してから再評価する（proposal §6・§7）。
- **JSON Schema の構造を変更した場合は `SCHEMA_VERSION`（03_step2_ai.md で定義する定数）もインクリメントする。** `schemaVersion` は冪等キーの構成要素であり、上げることで前版キャッシュを誤って再利用せず新規生成として再評価できる（4-3 参照）。

### 4-3. promptVersion の更新と再評価の回し方

1. プロンプト／スキーマを修正したら、`promptVersion` を上げる（例 v3 → v4）。
2. 冪等キー `reportId + imageSetHash + inputHash + promptVersion + modelId + schemaVersion` に `promptVersion`（および `schemaVersion`）が含まれるため、**`promptVersion`（またはスキーマ変更に伴う `schemaVersion`）が変われば冪等キーが変わり、新規生成として再実行される**（前版のキャッシュ結果を誤って再利用しない）。評価セットはテキスト入力も固定しているため `inputHash` は版間で同一になり、比較条件が保たれる。評価セットの各ケースを新 `promptVersion` で生成し直す。
3. ステップ2の KPI を再測定し、`results/<新promptVersion>_<測定日>.md` を追加保存（前版は残して版間比較できるようにする）。
4. 合格するまで 4-1〜4-3 を繰り返す。改善が頭打ちなら、工程6 のモデル A/B（Haiku 4.5 と Nova Lite 系）で品質×コストを比較する選択肢を検討（proposal §9 工程6・process.md §3、任意）。

## 失敗時の代替

- **KPI が改善しない（プロンプト／スキーマ調整の頭打ち）:** 評価セットの入力パターンを見直し、失敗ケースを分類し直す。それでも事実誤認が残る場合は、安全項目 UI を「AI は候補提示のみ・確定は人が必須」の運用でカバー（proposal §1・§2 のとおり最終判断は有資格者）。
- **写真起因の誤認が多い:** 写真を「補助材料」に徹させ、作業内容・進捗・翌日予定は**テキスト入力を主根拠**にする方針を強化（proposal §3）。数量など写真で確定不能な項目は最初から `要確認` 既定にする。
- **測定コストが高い（手評価が重い）:** 評価件数を各カテゴリ3件（合計12件）に絞り、代表・無関係カテゴリを優先。ただし件数を減らした旨と、率の粒度が粗くなる点を results に明記する（silent な縮小をしない）。
- **時間短縮率が測れない（ベースライン未整備）:** 代表写真3件だけでベースライン（手作業時間）を先に測り、補助指標として傾向のみ記録する。合格判定は必須3 KPI（充足率・事実誤認率・要確認）で行う。
- **フル KPI は S-tech をブロックしないが、ステップ0 のスモークは省略不可:** 期日制約でフル KPI（ステップ1〜4）を満たせない場合でも、S-tech 昇格はブロックされない。ただし**ステップ0 の最小品質スモークだけは必ず実施**して S-tech へ進み、フル KPI（S-accept の必須条件）は後追いで実施してよい（process.md v2 §2/§3）。

## process.md ゲートとの対応（再掲・明記）

- **ステップ0 の最小品質スモークは S-tech（技術共有可）の必須条件**である（process.md v2 §2 S-tech）。共有（EAS 内部配布／通しデモ）の前に必ず実施し、結果記録を S-tech の証拠として残す。
