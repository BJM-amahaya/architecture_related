## 0.5【v2 追記】AWS公式で確認できたこと

### ✅ (1) v1 の書き方は正しかった

公式のリクエスト例と、手元のコードが **完全に一致**していた。

| 経路 | 公式の欄名 | schema の渡し方 | 手元の状態 |
|---|---|---|---|
| Converse | `outputConfig.textFormat.structure.jsonSchema` | **JSON文字列**（`JSON.stringify` する） | `spike.ts` L94-106（コメントアウト中）が完全一致 ✅ |
| InvokeModel | `output_config.format` | **オブジェクトのまま**（stringify しない） | 本書 §5 の骨組みが完全一致 ✅ |

AWS SDK の型定義（`@aws-sdk/client-bedrock-runtime@3.1092.0`）とも一致することを確認済み。
→ **「書き方のミス」という線は消えた。**

> 💡 **2つの経路で schema の渡し方が逆**なので注意。
> Converse は**文字列**、InvokeModel は**オブジェクト**。ここを間違えると 400 になる。

### 🔴 (2) `jp.` を疑う根拠が消えた（v1 の前提がくつがえった点）

公式の「Supported APIs or features」表に、こう明記されている。

| 項目 | 対応 | 公式の注記 |
|---|---|---|
| Converse / ConverseStream | **Yes** | 会話型の推論 |
| InvokeModel / InvokeModelWithResponseStream | **Yes** | 単発の推論 |
| **Cross-Region inference（＝推論プロファイル）** | **Yes** | **「Works without any additional setup」** |
| Batch inference | Yes | 追加設定なしで動く |
| Anthropic Messages API（`bedrock-mantle` エンドポイント） | **No** | ここだけ `output_config.format` が 400 で拒否される |

**`jp.` は推論プロファイル＝Cross-Region inference。公式が「追加設定なしで動く」と言っている。**

v1 は「`jp.` が構造化出力に未対応かもしれない」という仮説で ②(b)/②(a) を組んでいたが、
**その仮説を支える根拠は公式ドキュメントに存在しなかった。**

さらに（※以下は検索結果ベースの二次情報。最終確認は AWS の「models at a glance」モデルカードで行うこと）：
- 構造化出力は **2026年2月に GA**
- **全ての商用AWSリージョン**で利用可能
- 対応モデルに **Claude Haiku 4.5 が含まれる**

→ **理論上は `spike.ts` のコメントを外すだけで通るはず。**
前回（7/24）失敗した理由は、ローンチ直後の段階的リリース等の可能性が高い。
**約10日経った今、まず再試行する価値が非常に高い。**

### 🆕 (3) 第2の正規経路「strict tool use」を発見

v1 が「代替（tool_use強制JSON）」として**弱く**扱っていた方法は、実は
**Bedrock 公式にサポートされた `strict: true` 機能**だった。

```jsonc
"toolConfig": { "tools": [ { "toolSpec": {
    "name": "submit_daily_report",
    "strict": true,                    // ← これが公式の構造化出力機能
    "inputSchema": { "json": { /* reportSchema をそのまま */ } }
} } ] }
```

公式いわく **「These mechanisms can be used independently or together」**
＝ JSON Schema 方式（`outputConfig`）と strict tool use は **対等な2つの正規手段**。

しかも **Converse のまま・`jp.` のまま・`toolConfig` を足すだけ**で試せる。
つまり「国内処理を維持できて、かつ変更コストが最小」という、旧②(b) より優れた選択肢。
→ **v2 ではステップ1に昇格。**

### ⚠️ (4) 追加で判明した注意点

| 項目 | 内容 | 影響 |
|---|---|---|
| **初回コンパイル** | 新しいスキーマは grammar のコンパイルに**最大数分**かかり得る | 工程0の「初回実測値」そのもの。ステップ0の1回目の時間を必ず控える |

| **スキーマ違反は即400** | サブセット外の機能を使うとコンパイル前に即エラー | §9 参照 |

## 3. ステップ1【🆕 v2】Converse + strict tool use（`jp.` 維持）

> 🔴 **ステップ0 実行結果：❌ 失敗（2026-08-04）**

そのまま写せる形にすると、こう：

| 入れる欄 | 値 | 注意 |

| `toolConfig.tools[0].toolSpec.strict` | `true` | **これが公式の構造化出力機能** |

> ✅ **SDK 型定義で存在を確認済み**（`@aws-sdk/client-bedrock-runtime@3.1092.0`）

## 5. ステップ3【旧②(b)】`jp.` + InvokeModel

`spike.ts` をコピー → `probe_invoke.ts`。`ConverseCommand` の代わりに `InvokeModelCommand` を使う。
**送り方の作法が3点違う**ので、そこだけ直す。

### Converse と InvokeModel の違い（ここが要点）

| 項目 | Converse（今の spike.ts） | InvokeModel（probe_invoke.ts） |
|------|--------------------------|--------------------------------|
| 画像の渡し方 | `bytes`（Uint8Array）そのまま | **base64文字列**に変換して渡す |
| 本文の渡し方 | SDKのオブジェクトのまま | **`body: JSON.stringify(...)`** で文字列化 |
| JSON強制の欄 | `outputConfig.textFormat`（schema は**文字列**） | **`output_config.format`**（schema は**オブジェクト**） |
| 応答の取り出し | `res.output.message...` | `res.body` を **デコードして JSON.parse** |

### ヒント（骨組み）※ v2 で公式例との一致を確認済み

```ts
import { BedrockRuntimeClient, InvokeModelCommand } from "@aws-sdk/client-bedrock-runtime";
import { readFileSync, readdirSync } from "node:fs";
import { join } from "node:path";

const MODEL_ID = "jp.anthropic.claude-haiku-4-5-20251001-v1:0"; // 国内処理を維持

// 画像は base64 文字列で渡す（Converse の bytes とは違う点）
function loadImagesBase64() {
  const files = readdirSync("./images").filter(f => /\.(jpe?g)$/i.test(f)).sort().slice(0, 5);
  return files.map(f => ({
    type: "image",
    source: {
      type: "base64",
      media_type: "image/jpeg",
      data: readFileSync(join("./images", f)).toString("base64"),
    },
  }));
}

const body = {
  anthropic_version: "bedrock-2023-05-31",
  max_tokens: 500,
  temperature: 0,
  messages: [
    { role: "user", content: [ { type: "text", text: "（spike.tsと同じ指示文）" }, ...loadImagesBase64() ] },
  ],
  // ▼ JSON強制（構造化出力）。InvokeModel ネイティブの正式な欄名は output_config.format
  output_config: {
    format: {
      type: "json_schema",
      schema: reportSchema,   // ← spike.ts の reportSchema オブジェクトをそのまま（stringify不要）
    },
  },
};

const command = new InvokeModelCommand({
  modelId: MODEL_ID,
  contentType: "application/json",
  accept: "application/json",
  body: JSON.stringify(body),      // ← 本文は必ず文字列化
});

const res = await client.send(command);
const decoded = JSON.parse(new TextDecoder().decode(res.body)); // ← 応答はデコードしてから読む
// decoded.content[0].text などに日報JSONが入る想定
```

> ✅ **【v2 更新】v1 の「要確認ポイント」は解消済み**。
> 上記 `output_config.format` の入れ子（`type` / `schema`）は AWS公式のリクエスト例と**完全一致**することを確認した。
> **このまま使ってよい。**

> ⚠️ ただし **InvokeModel の `body` は SDK 上ただの文字列**なので、**型チェックが一切効かない**。
> Converse と違い書き間違いに気付けないので、公式例と1文字ずつ照合すること。
> **推測でパラメータを足さない**（`.claude/CLAUDE.md` の禁止事項）。

### 実行
```bash
cd genbalog-spike
AWS_PROFILE=rag-app-admin npx tsx probe_invoke.ts
```

- ✅ 通れば → `jp.` + InvokeModel で実装。工程2はこの経路。
- ❌ ダメなら → §6 の「全滅」行へ。

## 9. スキーマ側の注意（v2 で公式情報を反映）

構造化出力の JSON Schema は **Draft 2020-12 のサブセットのみ**対応。

### ✅ 使えるもの（v2 で公式確認・v1 より広い）

- 基本型すべて：`object` / `array` / `string` / `integer` / `number` / `boolean` / `null`
- `enum`（文字列・数値・真偽値・null のみ）、`const`
- `anyOf`、`allOf`（制限あり）
- `$ref` / `$def` / `definitions` … **内部参照のみ**
- 文字列フォーマット：`date-time` / `time` / `date` / `duration` / `email` / `hostname` / `uri` / `ipv4` / `ipv6` / `uuid`
- 配列の `minItems` … **値 0 と 1 のみ**

### ❌ 使うと即400エラー

- `minLength` / `maxLength`（文字数制約）
- 数値制約（`minimum` / `maximum` / `multipleOf`）
- recursive schema（再帰的なスキーマ）
- **外部** `$ref` 参照
- `additionalProperties` が `false` **以外**

現行 `reportSchema`（`spike.ts` L18-53）は全項目 string＋ネスト1段＋`additionalProperties:false` で**準拠済み**。
工程2で項目を増やす時もこのサブセットを守ること。

> 💡 **v2 追記**：日付を扱うなら `"format": "date"` が使える（文字列フォーマットは対応）。
> ただし「文字数を50文字以内にする」等は**できない**（`maxLength` 非対応）。
> 文字数制限が必要なら `maxTokens` とプロンプトで制御する。

## ルール順守（重要）

- **本番は `jp.`（国内処理）**。`global.` は切り分け専用の一時確認に留める（データ国外流出リスク）。
  切り分けテストでも**実データは投入しない**。
- **新規パッケージ追加は不要**（`InvokeModelCommand` / `CountTokensCommand` は
  既存 `@aws-sdk/client-bedrock-runtime` に同梱）。
- **推測でパラメータを捏造しない**。v2 で AWS公式により確定した形以外は足さない。
