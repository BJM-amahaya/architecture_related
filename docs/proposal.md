# 現場AI日報「GenbaLog」提案書

建築業界向けプロトタイプ（デモアプリ） / Amplify Gen2 + CDK + Amazon Bedrock + React Native (Expo)

---

## 1. エグゼクティブサマリ

建築現場の監督・職人は、一日の終わりに **手書き／手入力で日報を作成** している。これは負担が大きく、記入漏れや報告遅延の原因にもなる。

**GenbaLog** は、現場で撮った写真と**最小限のテキスト入力（現場・日付・工種・当日メモ・翌日予定）** を AI（Amazon Bedrock / Claude）が解析し、**作業内容・進捗・安全上の懸念・翌日の予定** を含む日報ドラフトを自動生成する。写真は記述の補助・確認材料であり、写真単独で工程予定などの事実を確定させない（詳細は §3）。監督は内容を確認・微修正して確定するだけ。**「撮って書き足すだけで日報が仕上がる」** 体験を提供する。

- ターゲット：現場作業員・監督（スマホ中心 / 屋外利用）
- **必須環境：オンライン接続あり**（本PoC はオフライン下書き保存を要件外とする。弱回線対策は §6・§9 で扱う）
- 技術：AWS フルサーバーレス（Amplify Gen2 + CDK + Bedrock）+ React Native (Expo) モバイルアプリ
- コスト：固定サーバー費用なし。保存量・リクエスト・ビルドは従量課金。デモ規模なら **月額数ドル程度**（通常料金ベースの全サービス試算・前提は §5）

---

## 2. 解決する課題

| 現状の課題 | GenbaLog による解決 |
|---|---|
| 日報の手入力に毎日時間がかかる | 写真からAIが日報ドラフトを自動生成 |
| 現場での記録が後回しになり記憶頼み | その場で撮影 → 即ドラフト化 |
| 書式がバラバラで集計しづらい | 構造化された項目（作業/進捗/安全/翌日）で統一 |
| 安全上の懸念の見落とし | AIが写真から安全リスクの観点を提示（補助・参考。最終判断は有資格者） |

## 3. ソリューション概要（デモシナリオ）

**3ステップで日報が完成する：**

```
① 撮る＋書く          ② AI生成              ③ 確定
[写真＋最小テキスト入力]  [AIで日報生成 ボタン]    [内容を確認・微修正]
（現場/日付/工種/         │                      │
 当日メモ/翌日予定）  S3+DynamoDBへ保存    Bedrock(Claude)が      DynamoDBに保存
        │            └──────────┘   写真＋入力を解析しドラフト生成  → 一覧・PDF出力
```

**入力の考え方（事実性の担保）：**

写真から確認できない事項（工種、施工数量、作業員数、翌日の工程、口頭指示など）は写真だけでは確定できない。そこで**翌日の予定や作業実績の一次情報は最小テキスト入力を根拠**とし、写真は記述の裏付け・安全観点の補助材料に位置付ける。AI には次を守らせる：

- 画像・入力から確認できない項目は推測で埋めず、`要確認`／`不明`／空欄を返せるスキーマとプロンプトにする（JSON Schema は形式のみ保証し、内容の事実性は保証しないため）
- 安全項目は「**画像内で確認できた事項**」と「**画角外のため未確認**」を分離して出力し、「問題なし」を生成させない

**AIが生成する日報項目（例）：**
- 作業内容：「2F 床スラブの配筋作業を実施。」（当日メモを主根拠、写真で裏付け）
- 進捗：「基礎配筋 完了。」／数量が不明なら `要確認`
- 安全・懸念：「（確認できた事項）開口部の養生を確認。／（画角外・未確認）安全帯着用状況は写真外のため要確認。」
- 翌日の予定：「型枠建て込み、生コン打設の段取り。」（翌日予定入力を主根拠）

> ※ AI出力は参考・ドラフト。確定前に現場責任者／有資格者の確認を前提とする（安全項目を含む）。「撮って書き足すだけで仕上がる」の達成度は §9 の品質KPI（必須項目充足率・事実誤認率・修正文字率・作成時間短縮率）で受入判定する。

## 6. コスト制御・既知の制約（PoC前提）

低コストを「設計で担保する」ための前提とガードレール。

- **AppSync 30秒上限（最重要の技術リスク）**：日報生成は同期 custom query で実行するが、AppSync のリクエスト実行上限は30秒（変更不可）。「複数画像の取得＋Lambda コールドスタート＋Bedrock 推論」をこの中に収める前提とし、最大写真枚数で P95 応答時間を計測する。**弱回線での 30秒超過は中心ユースケースで起こり得る**ため、安定して満たせない場合は生成要求を受け付けて状態を返し、非同期（Lambda/SQS）＋クライアントポーリングへ切り替える。採否は §9 の技術スパイクで判定する。
- **Lambda のタイムアウトは「制御可能な deadline」で扱う（ハードタイムアウト依存の禁止）**：Lambda の設定タイムアウト（ハードタイムアウト）に達すると実行環境がリセットされ、`catch` による失敗状態の保存は**保証されない**。そのため Bedrock 呼び出しには `context.getRemainingTimeInMillis()` に基づく deadline（AbortSignal／SDK request timeout）を設定し、失敗保存・状態更新に必要な**後処理バッファ**を測定値に基づいて確保する。それでもハードタイムアウト・プロセス異常が起きた場合は、下記の lease 失効により後続の再試行で回復できる状態機械とする。この余裕を同期方式で安定確保できなければ非同期方式を主線にする。
- **Structured Outputs の API 固定と初回コンパイル**：構造化出力（Structured Outputs）は `bedrock-runtime` の **Converse / InvokeModel でのみ利用可能**で、Anthropic Messages API（`InvokeModel` の Anthropic ネイティブ形式ではない Messages 互換経路）では利用できないため、**利用APIを Converse または InvokeModel に固定**する。加えて AWS 公式では、**新しい JSON Schema の初回コンパイルに最大数分**かかり得、スキーマのキャッシュは初回アクセスから **24時間**。P95 だけでは初回・スキーマ変更後・キャッシュ失効後のタイムアウトを見落とす。対策として、**デプロイ後・スキーマ変更後に同一スキーマを事前コンパイルするウォームアップ**を用意し、24時間超の未使用後にも最大写真枚数で E2E 計測して AppSync 30秒以内を確認する（§9）。満たせなければ非同期方式へ切替。初回コンパイル中の再試行でも冪等性を維持し、UI に処理中／再試行可能状態を表示する。
- **写真・生成の制御（Bedrock コストの最大要因）**：1日報あたり写真は上限（例：3枚）、クライアント側で長辺1,568px に圧縮（Claude が API 側で自動縮小する上限に一致させ、無駄なアップロード帯域を削減）、出力は `maxTokens` で上限。日報4項目は構造化出力（JSON Schema 強制）で受け取り、パース失敗による再生成を設計で防止する（§5「平均生成回数 1.1回」の担保）。生成中はボタンを無効化し、冪等キー（**`reportId + imageSetHash + inputHash + promptVersion + modelId + schemaVersion`**）と **lease 付き生成状態**を DynamoDB に保存して、同一入力の再試行・二重送信で Bedrock を二重実行しない。`inputHash` は日報の一次情報であるテキスト入力（`reportDate/workType/memo/nextPlanInput`）をサーバー側で正規化してハッシュ化した値であり、**写真が同じでもメモ・翌日予定を変更すれば必ず新規生成される**（古いドラフトを返さない。データ完全性の要件）。`FAILED` や lease 期限切れの `RUNNING` は条件付き更新で再取得でき、即時再試行が可能。アップロードは MIME type・サイズ・枚数を、生成入力は日付・文字数上限をサーバー側でも検証する。
- **生成回数のサーバー側 quota**：再生成回数の上限は**サーバー側**（GenerationJobs または専用 quota レコード）で Report 単位・ユーザー×日次単位に条件付き更新で強制する。冪等ヒットは課金生成回数に含めず、新規 Bedrock 呼び出しだけを原子的に加算する。クライアントの回数表示・ボタン無効化は UX 補助であり、ガードレールの正本ではない。Lambda の reserved concurrency（小さめ）は全体上限の補助として実装初期（工程2）に設定する。AWS Budgets は**通知**であって呼び出し停止機構ではないため、アプリ側 quota と役割を分ける。
- **認可の再検証（IDOR 対策）**：custom query `generateReport` 内で、**認証主体（Cognito identity）と Report の所有者を再検証**する。クライアントから渡された任意の S3 key や `reportId` をそのまま信用せず、許可された Report に紐づくオブジェクトだけを Lambda に読ませる（他利用者の写真を読ませる IDOR を防止）。§4 の `allow.owner()`／`media/{entity_id}/*` と整合させ、guest/public API key・公開バケットは使わない。
- **保存とログの保持**：S3 写真は Lifecycle で短期 expiration（例：30日）＋未完了 multipart upload を1〜7日で abort。CloudWatch Logs の保持は7〜14日に固定し、画像やプロンプト本文を通常ログに出さない（ログに残す項目は §9 で定義）。
- **Bedrock リージョン／IAM（東京 In-Region 直接）**：本PoC は**東京リージョン（ap-northeast-1）で In-Region 直接呼び出し**を既定とし、モデルID `anthropic.claude-haiku-4-5-20251001-v1:0` を使う（Claude Haiku 4.5 は東京で In-Region に対応）。処理地域は東京。IAM は当該 foundation-model ARN への `bedrock:InvokeModel` を付与する（クロスリージョン推論プロファイルや APAC 各リージョンの ARN 許可は不要）。国内高可用性を後日優先する場合のみ日本 Geo 推論 `jp.anthropic.claude-haiku-4-5-20251001-v1:0`（推論プロファイル＋東京・大阪の foundation-model ARN 許可）へ切替可能。可用性・モデルIDは実装初日のゲートで疎通確認する（§9）。
- **必須環境（通信）**：本PoC は**オンライン接続ありを前提**とし、オフライン下書き保存（IndexedDB 等）・アップロード再開は要件外とする。弱回線での 30秒超過は上記 AppSync 対策（計測・非同期切替）で、二重送信は上記冪等キーで抑止する。低速回線・途中切断・再読み込み・同一写真の再送は §9 の異常系テストで検証する。
- **Free Tier の注意**：2025年7月15日以降に作成した AWS アカウントはクレジット方式の新 Free Tier。個別の無料枠を恒常前提にせず、通常料金ベースで見積もる（§5）。特に **AppSync の無料枠はアカウント作成から12か月**、**DynamoDB の 25GB は Standard テーブルのストレージ無料枠**（オンデマンドの読書き要求は従量。25 RCU/WCU 無料枠はプロビジョンド容量向け）。
- **コスト監視**：AWS Budgets で少額の月次予算＋複数閾値のメール通知を設定（Anthropic 課金を含むか確認）。Lambda は reserved concurrency を小さく設定し、暴走時の速度を抑える。

## 7. 技術的ポイント（チームPoCとしての学び）

- **Amplify Gen2** のコードファースト構成（`defineAuth/defineData/defineStorage/defineFunction`）でバックエンドを TypeScript 一元管理
- **CDK エスケープハッチ**：`backend.ts` から Lambda の IAM ロールに `bedrock:InvokeModel` と S3 read を付与（Amplify の標準範囲外を CDK で拡張する実践例）
- **Bedrock マルチモーダル**：Claude Haiku 4.5（東京 In-Region・`anthropic.claude-haiku-4-5-20251001-v1:0`）に現場写真を画像入力として渡し、構造化された日報項目を日本語生成
- **構造化出力（structured outputs）**：日報4項目（作業/進捗/安全/翌日）を JSON Schema で出力形式ごと強制。パース処理が不要になり、形式崩れによる再生成コストも防げる。**`bedrock-runtime` の Converse / InvokeModel で利用**（Messages API 経路では不可）。初回スキーマコンパイル（最大数分）とキャッシュ24時間の制約は §6 のウォームアップで吸収する
- **個人サンドボックス**（`npx ampx sandbox`）でチーム各自が独立検証可能
- **React Native (Expo) フロント**：`aws-amplify` + `@aws-amplify/ui-react-native` でAmplify Gen2バックエンド（Cognito/AppSync/S3）に直接接続。カメラ・写真取得は `expo-camera` / `expo-image-picker`、アップロード前の圧縮は `expo-image-manipulator` で長辺1,568px にリサイズ
- **EAS Build**：Expoのクラウドビルドで開発ビルド・内部配布を作成。PoC段階では Expo Go / 開発ビルドでの内部確認に留め、正式な App Store / Google Play 申請は行わない（§5）

## 9. 作業計画（実装順序・依存関係・完了条件）

手戻りの大きい技術リスク（同期方式の可否）を先に潰すため、**技術スパイクを最優先**し、その結果で同期／非同期を確定してから UI まで作り込む。各工程に成果物・完了条件・失敗時の代替案を付す。

**工程0：技術スパイク（最優先・実装初日ゲート）**
- 内容：東京 In-Region の `anthropic.claude-haiku-4-5-20251001-v1:0` に対し、**Converse/InvokeModel・Structured Outputs・画像入力を1リクエストで疎通**。新規スキーマの**初回コンパイル**と、最大写真枚数（5枚）・24時間超未使用後の E2E レイテンシを計測。
- 成果物：モデル可用性・IAM 疎通の確認記録、**初回コンパイルの実測値（最大値。1標本のため P95 は算出しない）**・**定常 P95（同一スキーマ・同一入力条件の複数回測定に限定）**・24時間後再計測の単一値、実測 usage トークン。
- 完了条件：疎通成功、AppSync 30秒以内の可否が数値で判定できる、かつ**採用方式（同期／非同期）の設計・手順が実装着手可能な状態**になっている（非同期採用時は `03b_step2_async.md` の手順で着手できること）。
- 失敗時：30秒以内が安定しなければ**非同期（Lambda/SQS＋ポーリング）を採用**。**同期継続の判定基準＝「初回コンパイルの実測最大値 < 25秒、またはウォームアップにより初回コンパイルを利用者経路から確実に除外できること」かつ「定常 P95 に十分な余裕があること」**。判断日と判定結果をこの工程で確定し、UI 実装前に決める。ウォームアップ失敗・24時間未使用後の初回利用を許容できない場合は非同期方式へ倒す。

**工程1：認可付き Data／Storage**
- 内容：`Site`/`Report`/`Photo` を `allow.owner()`、S3 を `media/{entity_id}/*` で本人分離。Block Public Access 有効化。
- 完了条件：`npx ampx sandbox` デプロイ成功（CloudFormation 成功）、Cognito ログイン → 現場登録 → 写真アップロード（S3 保存確認）。
- 失敗時：認可規則を owner 明示に修正して再デプロイ。

**工程2：AI処理（generateReport）**
- 内容：工程0で確定した同期／非同期方式で custom query を実装。所有者・S3 key 再検証（IDOR 対策）、冪等キー（`inputHash` 込み）、**lease 付き状態機械（`FAILED`・lease 期限切れ `RUNNING` の即時再試行回復）**、**制御可能な deadline（残り時間ベースの AbortSignal＋後処理バッファ）**、**サーバー側生成 quota（Report 単位・ユーザー×日次）**、**生成入力のサーバー側検証（日付・文字数）**、Structured Outputs、ウォームアップ手順、reserved concurrency の初期設定。
- 完了条件：「AIで日報生成」→ Bedrock がドラフト返却、確定保存 → DynamoDB レコード作成を確認。写真同一のままメモ・翌日予定を変更した再生成が**新規生成**になること、`FAILED` 後の再試行が成功することを確認。ログに §末の記録項目のみ出力。
- 失敗時：初回コンパイルで超過するならウォームアップ追加、なお超えるなら非同期化。

**工程3：UI 統合**
- 内容：撮影＋最小テキスト入力 → 生成 → 確認・微修正 → 確定 → 一覧・PDF出力。生成中ボタン無効化・処理中/再試行状態表示。**Report 作成後は編集画面 `/reports/{reportId}/edit` へ遷移し、`reportId` を URL（ルートパラメータ）に永続化**する——アプリ再起動・画面再読み込み後も Report 本体・写真・入力値・ドラフト・生成状態を再取得して完全復元できることを要件とする（React state だけに依存しない）。日付は当日を既定値とし、写真 UI は Report 作成後に有効化する（必須項目と作成順の整合）。PDF は**アプリ内PDF生成（expo-print 等）でのクライアント側生成を既定**とし、Lambda PDF 生成は行わない（追加コスト・依存回避）。配布は Expo Go / 開発ビルドによる内部確認に留め、正式なストア申請は行わない（§5・§7）。
- 完了条件：一覧表示・PDF出力、およびアプリ完全再起動後の状態復元を確認。

**工程4：品質評価（AI出力の合否判定）**
- 内容：**固定評価セット**（代表写真／不鮮明写真／無関係写真／情報不足写真）で、必須項目充足率・**事実誤認率**・要確認率・修正文字率・作成時間短縮率を測定。
- 完了条件：合格値（例：充足率≥90%、事実誤認率≤5%、要確認項目が推測で埋まらない）を満たす。§1「撮って書き足すだけで仕上がる」の受入基準（= `process.md` の **S-accept** 条件）。なお共有前（**S-tech**）には、フル評価とは別に**最小品質スモーク**（無関係・不鮮明写真とテキスト欠落入力で捏造しない／安全項目で「問題なし」を生成しない）を必須とする（`process.md` §2）。
- 失敗時：プロンプト／スキーマ（`要確認`許容・安全項目の確認/未確認分離）を調整。

**工程5：異常系テスト（受入条件）**
- 認可違反（他ユーザーIDの `reportId`／S3 key を指定した**否定テスト**が拒否される）、Bedrock throttle/timeout、Lambda 再実行、AppSync timeout、S3 アップロード失敗、重複クリック（冪等抑止）、**`FAILED` 後の再試行成功・lease 期限切れ `RUNNING` の takeover 成功**、**写真同一のままメモ／翌日予定を変更した再生成が新規生成になり旧結果を返さない**、低速回線・途中切断・**「生成要求送信前／生成実行中／生成完了直後／確定前」の各時点でのアプリ完全再起動からの状態復元**・同一写真の再送。
- 完了条件：いずれも情報漏えい・二重課金・不整合が発生しない。

**工程6：実測コスト更新**
- 内容：Bedrock CountTokens もしくは実レスポンス usage で実測入力／出力トークンを記録し、§5 の概算式と全サービス月額表（標準／上振れ）を更新。
- 完了条件：標準ケースが「実質 月額数ドル以内」に収まることを実測で確認。
- **モデルA/B（任意）**：同一写真セットで Claude Haiku 4.5 と低コスト画像モデル（Amazon Nova Lite 系）を比較し、項目充足率・安全指摘・日本語品質・P95 latency・1件単価を評価。品質基準を満たす最安モデルを既定にする。

**ログに記録する項目（証拠・再現性の担保）：** 画像・プロンプト本文は残さず、request ID・report ID の**非可逆識別子**・モデルID・latency・usage トークン・結果状態・冪等/重複抑止結果を記録する（§6「プロンプト本文を通常ログに出さない」と整合）。
