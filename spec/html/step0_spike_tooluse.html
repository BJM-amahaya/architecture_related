構造化出力を outputConfig から Tool Use 方式へ切り替えた記録

Bedrock の Claude Haiku 4.5 で JSON Schema 強制が使えなかった原因と、その回避方法・実測値をまとめます。

対象ファイル：genbalog-spike/spike.ts　/ 結論：疎通成功　/ 方式：Tool Use（toolConfig）

1. 3行でわかるサマリー

  1. 何が起きたか：日報を決まった形（JSON）で返させる設定を入れたら、API がエラーで止まった。
  2. 原因：Bedrock 上の Claude Haiku 4.5 が、その設定項目（outputConfig）に対応していなかった。
  3. 対処：同じ目的を果たせる別の仕組み「Tool Use」に切り替えて、疎通に成功した。

なぜこの数字が重要か

本プロジェクトの最大リスクは AppSync の 30 秒タイムアウトです。写真 2 枚で 3.5 秒なら余裕がありますが、 枚数と画像サイズを増やすと伸びます。この値は「同期処理でいけるか／非同期にすべきか」を決める入力データになります。

2. 発生していたエラー

$ AWS_PROFILE=rag-app-admin npx tsx spike.ts
=== 疎通失敗 ===
ValidationException The model returned the following errors: output_config.format: Extra inputs are not permitted
用語補足　ValidationException ＝「リクエストの内容が不正です」というエラー。 Extra inputs are not permitted は直訳すると「余分な入力は許可されていません」で、 受け取る側が知らない項目が入っていたことを意味します。

3. 原因調査：4つの経路をすべて試した

最初に疑ったのは「モデルの呼び出し経路（推論プロファイル）が悪いのでは？」という点でした。 そこで MODEL_ID の接頭辞だけを変えて 4 パターン試しました。

#MODEL_ID結果エラー内容
1jp.anthropic.claude-haiku-4-5-…失敗output_config.format: Extra inputs are not permitted
2apac.anthropic.claude-haiku-4-5-…失敗同上
3global.anthropic.claude-haiku-4-5-…失敗同上
4anthropic.claude-haiku-4-5-…（接頭辞なし）失敗別のエラー：on-demand throughput isn't supported
ここが推理のポイント

4番目だけエラーの文言が違います。これは失敗の種類が違うことを示しており、 「原因は経路ではなくモデル側にある」と言い切るための決定的な手がかりになりました。

4. なぜ「モデル側が原因」と言い切れるのか

リクエストは spike.ts → Bedrock（AWS の受付窓口） → Claude 本体 の順に流れます。 4パターンは、どこまで届いたかが違っていました。

たとえ話

申込書に「備考欄」を書いて窓口へ出しました。3つの支店（jp / apac / global）はどこも受け取って奥へ回してくれましたが、 奥の担当者（Claude Haiku 4.5）が毎回「うちの様式に備考欄はありません」と突き返してきた——という状況です。 4つ目は窓口自体が閉まっていた（別の話）。
つまり、支店を変えても解決しません。様式そのものを変える必要がありました。

5. 確定した原因

Bedrock 上の Claude Haiku 4.5 は outputConfig.textFormat（Structured Outputs）に対応していない

Anthropic の API 単体では Haiku 4.5 でも構造化出力は使えますが、 Amazon Bedrock 経由で提供されているこのモデルでは有効化されていません。 SDK のバージョンやコードの書き方の問題ではないことは、型定義 （@aws-sdk/client-bedrock-runtime の OutputConfig.textFormat）と 完全に一致していたことから確認済みです。

6. 対処：Tool Use 方式に切り替える

Claude には「ツール（関数）を呼び出す」という別の仕組みがあります。 ツールには「引数はこの形で渡してください」というスキーマを定義でき、 さらに toolChoice で「必ずこのツールを呼べ」と指定できます。

発想の転換　「決まった形で答えてほしい」→ 直接指定は不可。
そこで「決まった形の引数でツールを呼ばせる」→ 結果的に同じ JSON が手に入る。

7. 変更点の一覧

箇所BeforeAfter理由
MODEL_ID 接頭辞なし jp. 付きに復帰 接頭辞なしは「推論プロファイル必須」で門前払いされるため
スキーマの渡し方 JSON.stringify() した文字列 オブジェクトのまま inputSchema.json はオブジェクトを受け取る仕様
送信先フィールド outputConfig.textFormat toolConfig.tools[].toolSpec モデルが output_config 非対応
強制の方法 type: "json_schema" toolChoice: { tool: {…} } 「必ずこのツールを呼べ」＝結果的にスキーマ強制
結果の取り出し content[0].text → JSON.parse content[].toolUse.input input は最初からオブジェクト。parse 不要
maxTokens 500 1500 ツール引数の JSON も出力トークンを消費するため
異常系 なし toolUse 不在時に throw 「動いたが中身が空」を見逃さないため

実際のコード（抜粋）

// JSON Schema 強制。Bedrock の Claude Haiku 4.5 は outputConfig.textFormat
// （Structured Outputs）に非対応のため、Tool Use で代替する。
toolConfig: {
  tools: [
    {
      toolSpec: {
        name: TOOL_NAME,
        description: "建築現場の日報4項目（作業/進捗/安全/翌日）",
        // outputConfig と違い、スキーマはオブジェクトのまま渡す（stringify しない）
        inputSchema: { json: reportSchema },
      },
    },
  ],
  toolChoice: { tool: { name: TOOL_NAME } },  // 必ずこのツールを呼ばせる
},
// Tool Use の結果は content の toolUse ブロックに入る。
// input は既にオブジェクトなので JSON.parse は不要。
const toolUse = res.output?.message?.content?.find(
  (block) => block.toolUse?.name === TOOL_NAME,
)?.toolUse;

if (!toolUse?.input) {
  // 黙って undefined を返すと「動いたが中身が空」を見逃すため、明示的に落とす。
  throw new Error(`ツール呼び出しの結果を取得できませんでした（stopReason: ${res.stopReason}）。`);
}

8. ハマりどころ 3点

① JSON.stringify を必ず外す

outputConfig はスキーマを文字列で受け取りましたが、 inputSchema.json はオブジェクトで受け取ります。 そのまま移植すると「文字列が入ったスキーマ」という壊れた形になります。

② strict: true は最初は付けない

toolSpec.strict も Structured Outputs 系の機能なので、 output_config と同じく拒否される可能性があります。 まず素の状態で疎通を確認し、通ってから追加して試すのが安全です（コード内にコメントで明記済み）。

③ 結果の取り出し先と stopReason が変わる

stopReason は "end_turn" ではなく "tool_use" になります。 ここを見て分岐している処理があると動かなくなるので注意してください。

確認できたこと

  • Bedrock への疎通が成功した
  • stopReason: tool_use ＝ ツールが確実に呼ばれた
  • 日報4項目がスキーマ通りに揃った（work_content / progress / safety_concern / next_day_plan）
  • safety_concern が confirmed / unconfirmed に分離されている
  • 型チェック（tsc --noEmit）がエラー 0 件で通る
⚠ 未検証：日報生成の「品質」

images/ に入っていたテスト画像 2 枚が建築現場の写真ではありませんでした （モデルは「桃の食材写真」と判定）。 そのため今回証明できたのは API 疎通・スキーマ強制・レイテンシ までで、 日報の中身が実用に足るかは未検証です。この点を工程0の合否判定で混同しないでください。

✓ 副産物：事実性ガードは機能している

現場写真でないと判断した上で、モデルは推測で日報をでっち上げず全項目を「要確認」と返しました。 これは提案書で定めた「確認できない事項は推測で埋めない」という要件が、 プロンプトで正しく効いていることの証拠になります。
